# 广告设计公司客户对接平台 1.0 技术文档

版本：1.0  
日期：2026-07-20  
阶段定位：项目骨架、页面框架、基础功能与演示数据

## 1. 技术目标

1.0 版本优先建立稳定、清晰、可扩展的前后端工程骨架，保证后续 2.0、3.0 可以继续在现有结构上补齐复杂功能。

本阶段技术目标：

1. 后端项目可启动，具备基础 REST API、登录鉴权、演示数据和统一返回结构。
2. 客户前台/客户端可启动，具备首页、作品集、案例详情、登录、项目列表、沟通工作台、项目详情页面。
3. 设计师端可启动，具备登录、项目列表、沟通工作台、项目详情页面。
4. 前后端具备基础接口联调能力。
5. 状态机、文件上传、实时通讯等复杂能力先预留模型和接口边界，不在 1.0 做生产级实现。

## 2. 项目结构

当前仓库按三个子项目组织：

```text
advertisement_Design/
├── advertisement_Design_back/    # 后端服务
├── advertisement_Design_user/    # 访客 + 客户端
├── advertisement_Design_client/  # 设计师端
├── docs/                         # 项目文档
├── README.md
└── 项目.docx
```

目录职责：

- `advertisement_Design_back`：提供用户认证、作品案例、项目、会话、消息、阶段状态等 API。
- `advertisement_Design_user`：提供访客首页、作品集、客户登录、客户项目和客户沟通工作台。
- `advertisement_Design_client`：提供设计师登录、设计师项目管理和设计师沟通工作台。
- `docs`：存放需求、技术、使用、测试、部署、业务流程和复盘文档。

## 4. 后端模块设计

### 4.1 模块划分

后端建议按以下模块组织：

- `auth`：登录、注册、JWT 生成与校验。
- `user`：用户信息和角色。
- `portfolio`：作品案例列表、筛选、详情。
- `project`：项目列表、项目详情、进度信息。
- `conversation`：会话列表。
- `message`：消息查询和文字消息发送。
- `stage`：业务阶段和阶段状态查询。
- `common`：统一响应、异常处理、分页、常量、枚举。

### 4.2 统一返回结构

所有 API 使用统一 JSON 返回结构：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

约定：

- `code = 0` 表示成功。
- 非 0 表示业务错误或系统错误。
- `message` 用于展示错误信息。
- `data` 承载具体业务数据。

### 4.3 用户与角色

角色枚举：

| 枚举值 | 含义 |
| --- | --- |
| VISITOR | 访客，不落库或不登录 |
| CUSTOMER | 客户 |
| DESIGNER | 设计师 |

1.0 至少内置两套演示账号：

| 角色 | 账号 | 密码 |
| --- | --- | --- |
| CUSTOMER | customer@example.com | 123456 |
| DESIGNER | designer@example.com | 123456 |

密码存储要求：

- 即使是演示版本，也应使用 BCrypt 等方式加密存储。
- 不应在接口返回密码字段。

### 4.4 后端编码规范

本项目后端开发必须遵守项目专属 skill：`skills/ad-springboot-backend-standards`。该 skill 只适用于当前项目，不作为全局规范使用。

技术栈约束：

- 后端使用 Spring Boot 3.2、Java 17。
- ORM 使用 MyBatis-Plus 3.5。
- 数据库使用 MySQL 8.0。
- 工具使用 Lombok、MapStruct。

代码分层约束：

- Controller 层统一返回 `Result<T>` 包装类。
- Controller 不得直接返回 Entity。
- Controller 禁止编写业务逻辑，必须下沉到 Service。
- Service 负责业务规则、事务边界、权限校验、状态流转和 Mapper 协调。
- Mapper 使用 MyBatis-Plus `BaseMapper<T>`。
- 优先使用 Java Config，不使用过时 XML 配置。

对象边界约束：

- Entity 只用于数据库映射和 Service/Mapper 内部流转。
- 请求参数使用 Request DTO。
- 响应数据使用 Response VO。
- Entity、DTO、VO 之间的常规转换优先使用 MapStruct。

实体类规范：

- 所有实体类必须使用 Lombok 的 `@Data`、`@Builder`。
- 使用 `@Builder` 且需要无参构造时，补充 `@NoArgsConstructor`。
- 使用 `@Builder` 且需要全参构造时，补充 `@AllArgsConstructor`。
- 数据库字段使用下划线命名，例如 `user_name`。
- Java 字段使用驼峰命名，例如 `userName`。
- 实体类使用 MyBatis-Plus 注解声明表名和主键，例如 `@TableName`、`@TableId`。

API 规范：

- 所有 API 接口必须添加 Swagger/OpenAPI 注解。
- Controller 类需要添加类级 OpenAPI 注解。
- Controller 方法需要添加方法级 OpenAPI 注解。
- 接口路径统一以 `/api` 开头。
- 新增接口时同步补齐 DTO/VO、Service 方法、必要 Mapper 调用和 OpenAPI 注解。

安全规范：

- 密码必须使用 BCrypt 加密。
- 禁止明文保存密码。
- 禁止在日志、异常信息或接口响应中输出密码、密码哈希、token 密钥等敏感数据。
- 后端接口必须做角色和数据权限校验，不能只依赖前端路由守卫。

### 5.7 预留基础表

数据库作为项目基石，1.0 建库时需要提前创建 2.0、3.0 必然会用到的基础表，避免后续大规模重构。1.0 业务代码可以暂时不完整使用这些表，但表结构需要随 `docs/数据库.sql` 一起初始化。

预留表清单：

| 表名 | 用途 | 对应后续能力 |
| --- | --- | --- |
| file_asset | 统一文件资产表，记录上传人、存储位置、MIME、大小、哈希和状态 | 文件上传、MinIO/OSS、合同 PDF、阶段归档 |
| message_file | 消息与文件关联表 | 图片消息、文件消息、附件消息 |
| conversation_read_state | 会话级已读状态表 | 已读/未读、未读数、会话列表提醒 |
| stage_action | 阶段确认动作表，记录发起人、确认人、确认/驳回说明和时间 | 双方确认状态机、阶段流转留痕 |
| project_file | 项目文件归档表，关联项目、阶段和文件资产 | 阶段产物归档、客户下载交付物 |
| operation_log | 操作日志表，记录关键业务动作前后状态 | 审计、复盘、问题排查 |

关键设计原则：

- `project_stage` 保存项目当前阶段状态，适合列表和详情展示。
- `stage_action` 保存每次阶段发起、确认、驳回记录，适合追溯完整流程。
- `file_asset` 只描述文件本身，`project_file` 和 `message_file` 描述文件用于哪个业务场景。
- 已读未读不直接写在 `message` 表，使用 `conversation_read_state` 记录每个用户在每个会话中的阅读进度。
- `operation_log` 记录关键操作，不替代业务表，只用于审计和排查。

## 8. 登录与权限方案

1. 用户提交邮箱和密码。
2. 后端校验账号密码。
3. 后端返回 JWT 和用户信息。
4. 前端保存 token 和用户信息。
5. 前端请求受保护接口时携带 `Authorization: Bearer <token>`。
6. 后端解析 token，识别用户 ID 和角色。
7. 前端路由守卫根据角色限制页面访问。
8. 后端接口必须再次校验数据权限，不能只依赖前端守卫。

1.0 可将 token 存储在 `localStorage`，后续版本再按安全要求优化为更严格的存储方式。

## 9. 状态与流程设计

1.0 需要建立阶段数据结构和展示逻辑，但不强制实现完整状态流转。

阶段展示规则：

- 按固定顺序展示 7 个阶段。
- 当前项目返回每个阶段的状态。
- 前端根据状态显示不同颜色和文案。
- 项目进度可根据已达成阶段数量计算。

进度计算规则：

```text
progress = 已达成阶段数量 / 7 * 100
```

如果后端项目表中已有 `progress` 字段，则以后端字段为准；如果没有，则前端可根据阶段列表临时计算展示。

## 10. 演示数据

1.0 后端启动后应具备演示数据，至少包括：

- 用户：演示客户、演示设计师。
- 作品案例：不少于 6 条。
- 项目：不少于 2 个。
- 会话：每个项目 1 个会话。
- 消息：每个会话不少于 5 条，包括系统消息。
- 阶段：每个项目包含 7 个阶段，覆盖待发起、等待确认、已达成、已驳回等状态。

种子数据可以通过以下方式之一实现：

- SQL 初始化脚本。
- 后端启动时初始化。
- 本地 JSON 导入。

推荐 1.0 使用 SQL 初始化脚本，便于部署文档和演示环境复现。

## 11. 错误处理

后端基础错误码：

| code | 含义 |
| --- | --- |
| 0 | 成功 |
| 400 | 请求参数错误 |
| 401 | 未登录或 token 无效 |
| 403 | 无权限 |
| 404 | 资源不存在 |
| 500 | 系统异常 |

前端处理要求：

- 401 跳转登录页。
- 403 显示无权限提示。
- 表单参数错误在当前页面提示。
- 网络错误显示统一提示。
