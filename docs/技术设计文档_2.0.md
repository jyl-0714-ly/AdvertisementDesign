# 广告设计项目协作平台技术设计文档

版本：2.0  
日期：2026-07-28  
状态：目标架构草案  
需求依据：`docs/需求分析报告_2.0.md`

## 1. 文档目标

本文定义新版“项目优先、会话承载、七阶段持续服务”平台的目标技术架构。它取代旧版以作品顾问、咨询需求单、三秒匹配和六十秒确认为主线的技术方向，但不代表立即删除现有代码。系统应通过受控迁移逐步建立新模型，在验证数据和调用方迁移完成后下线旧能力。

## 2. 架构原则

系统采用模块化单体：一个 Spring Boot 应用、一个主要部署单元和一个 MySQL 数据库。模块之间通过公开应用服务、命令／查询对象或领域事件协作，禁止跨模块直接访问 Mapper、Entity 或业务表。

架构必须同时满足以下原则：

- 项目是业务聚合根，会话、阶段、成员、计划、文件和商业记录均在项目上下文中授权。
- 客户侧显示身份与后台真实执行主体分离。
- 阶段推进由状态机和真实事件驱动，不由聊天文本直接决定关键状态。
- 关键对象版本不可变，修订产生新版本。
- 外部签署、支付和通知采用适配器隔离，回调幂等。
- 自动化能力采用最小权限工具授权，不可逆动作需要人工决策。
- 全流程审计不依赖普通应用日志。
- 优先保持结构清楚和可维护性，不为可能的未来场景提前拆微服务。

## 3. 技术栈

后端使用 Java 17、Spring Boot 3.2、Spring Security、JWT、MyBatis-Plus 3.5、MySQL 8.0、Lombok、MapStruct、Jakarta Validation 和 Swagger/OpenAPI。

客户前端 `advertisement_Design_user` 与设计师前端 `advertisement_Design_stylist` 使用 Vue 3、Vite、TypeScript、Vue Router、Pinia、Axios 和 Element Plus。当前只要求桌面端体验。

文件物理存储通过 `common.storage` 适配对象存储，继续采用后端受控上传。消息实时性可在普通 HTTP 基础能力稳定后引入 WebSocket；WebSocket 只是通信适配方式，不拥有业务状态。

## 5. 后端业务模块

目标顶层模块如下：

```text
com.advertisementdesign.back
├── auth
├── identity
├── portfolio
├── project
├── communication
├── workflow
├── artifact
├── commercial
├── automation
├── notification
└── common
```

各模块职责如下：

- `auth`：登录、注册、验证码、JWT、Spring Security 认证流程。
- `identity`：用户、客户组织、设计师资料、角色、项目成员与授权模型。
- `portfolio`：公开作品案例、筛选、发布与展示。
- `project`：项目主数据、项目名称、状态、负责人分配、暂停、恢复、终止请求和可复用项目摘要。
- `communication`：项目会话、消息、显示身份、真实发送主体、已读状态和聊天附件关联。
- `workflow`：七阶段实例、阶段事件、任务、真实事件门槛、受控回退和项目计划。
- `artifact`：需求基线、报告、草图、正式设计、交付物、统一版本、标注和确认。
- `commercial`：报价、合同、电子签、支付、变更单和退款／终止计算结果。新版商业流程已成为真实业务，不再作为空预留模块。
- `automation`：协调 Agent、七阶段 Agent、执行记录、知识访问、工具授权、人工接管、升级和运行诊断。
- `notification`：站内与邮件通知、提醒、SLA 触发和送达结果。
- `common`：统一返回、异常、审计基础设施、幂等、时钟、通用安全上下文、底层文件存储及外部适配基础，不包含业务规则。

现有 `consultation` 模块属于旧方向。迁移期间可以保留，但禁止继续把新项目需求建立在旧咨询需求单或匹配状态机上。其仍有价值的需求结构化、摘要或调度代码，应迁入新业务所有者模块，而不是整体改名继续使用。

## 6. 模块依赖与集成方式

推荐主要依赖方向：

```text
auth          -> identity, common
portfolio     -> common
project       -> identity, common
communication -> identity, project, common
workflow      -> project, identity, common
artifact      -> project, identity, common
commercial    -> project, identity, artifact, common
automation    -> 各模块公开应用服务, common
notification  -> identity, project, common
common        -> 不依赖业务模块
```

`automation` 不得直接操作各模块 Mapper 或表，只能调用受控应用服务或发布命令。模块反向通知优先采用事务后事件或 Outbox 事件，避免循环依赖和“数据库已提交但通知未发送”的不一致。

## 7. 核心领域模型

以下模型表达业务职责，不要求一次迭代全部落表。实施前应结合现有数据库编写迁移设计。

### 7.1 项目与参与者

`Project` 记录客户组织、名称、名称来源、当前阶段、项目状态、主要联系人、主负责设计师及时间信息。名称来源至少区分 `AUTO` 和 `MANUAL`，手动命名后自动命名器不得覆盖。

`ProjectConversation` 与项目一对一，存储最近消息和活动时间。第一条有效需求触发项目与会话同事务创建。

`CustomerProjectMember` 记录客户成员角色与专项权限。`ProjectAssignment` 记录主负责和协作设计师、授权范围、生效区间、发起与接受信息。历史分配不可覆盖。

设计师全局列表查询只返回必要摘要。读取完整会话、文件和商业数据时，权限服务必须验证主负责、授权协作或管理员身份。

### 7.2 消息与身份

`Message` 至少记录：会话、消息类型、内容、客户显示身份、真实 actor 类型、真实 actor ID、生成／发送来源、回复关系、发送时间和状态。

真实 actor 类型可包含 `CUSTOMER_USER`、`DESIGNER_USER`、`ADMIN_USER`、`COORDINATOR_AGENT`、`STAGE_AGENT` 和 `SYSTEM_EVENT`。客户侧团队消息的显示身份固定映射为“项目服务团队”，但真实 actor 永远保留。客户成员消息根据 `CUSTOMER_USER` 和项目成员关系展示其真实项目成员名称；查询时仍须执行组织与项目授权，不得从消息字段信任任意客户端显示名。

一条消息可关联多个 `MessageAttachment`。附件在发送前保持客户端草稿或受当前用户约束的短期上传状态，客户可查看待发送列表并移除误选文件；只有消息发送成功后，附件关系才绑定到该项目会话。未发送草稿必须按保留策略清理，不能成为可被其他项目引用的业务附件。

消息一经发送不可原地修改正文。错误通过 `CORRECTION` 类型的新消息关联原消息。删除仅允许受控的合规隐藏或逻辑撤回，并保留审计记录。

### 7.3 阶段与事件

七阶段代码固定为：

```text
REQUIREMENT_GUIDE
CONTRACT_PREPAYMENT
RESEARCH_REPORT
SKETCH_STYLE
REVIEW_FINAL
DELIVERY_FINAL_PAYMENT
AFTER_SALE_REPURCHASE
```

`ProjectStageInstance` 保存每个项目各阶段的当前展示状态、激活次数和计划时间。`ProjectStageEvent` 以追加方式保存激活、等待、完成、重开、暂停和恢复事件。禁止只覆盖一个状态字段而丢失历史。

项目状态与阶段状态分离。建议阶段状态包括 `NOT_STARTED`、`ACTIVE`、`WAITING_CUSTOMER`、`PROCESSING`、`UNDER_REVIEW`、`CHANGE_PROCESSING`、`COMPLETED` 和 `SUSPENDED`。

状态机迁移必须通过明确命令，校验当前状态、权限、绑定版本和真实事件。受控回退通过新增 `REOPENED` 事件和新的激活轮次实现，不反向删除已完成事件。

### 7.4 产物、版本与确认

`Artifact` 表示业务产物逻辑身份，类型包括需求基线、报价、合同、调研报告、草图、正式设计、变更单和交付包。`ArtifactVersion` 是不可变版本，记录内容、文件清单、创建来源、审核状态、发布时间和父版本。

通用 `ConfirmationAction` 记录被确认对象、版本、动作类型、真实客户操作人、授权依据、时间和结果。每类确认仍由所属模块执行具体业务规则，不能仅插入一条通用记录就完成状态迁移。

`ArtifactAnnotation` 绑定文件资产和具体版本，保存坐标化标注、结构化说明及提交者。

### 7.5 商业对象

`Quote`／`QuoteVersion` 保存规则依据、金额、有效期和异常审批。`Contract`／`ContractVersion` 保存合同版本和签署要求。`SignatureEvent` 保存外部签署请求和回调事实。

`PaymentOrder` 表示应付款项，`PaymentEvent` 保存渠道回调与状态变化。支付成功必须来自已验证、幂等处理的外部结果，不由客户端传入“成功”状态。

`ChangeOrder` 保存需求基线、合同版本、范围、费用和计划影响。`ProjectTerminationRequest` 保存终止申请、合同规则计算结果和人工决定。退款和争议结论必须记录授权人工主体。

### 7.6 自动化与接管

`AgentExecution` 记录所用 Agent、输入上下文引用、输出、置信度、知识引用、工具调用和执行结果；敏感上下文不得直接复制到普通日志。

`HumanTakeoverSession` 记录项目、接管人、开始／结束时间、原因及状态。一个项目同时只能有一个有效回复控制权。接管开始后自动回复必须暂停；恢复前协调 Agent 读取完整会话和内部干预记录。

`AgentEscalation` 记录低置信度、需求冲突、客户不满、支付异常、阶段超时等风险及处理状态。

### 7.7 客户可复用资料

`CustomerReusableProfile` 保存经允许复用的组织、品牌和偏好事实，并记录来源、置信度、客户纠正和可见范围。新项目按相关性引用，不把旧项目业务记录复制为新项目事实。

## 8. 关键用例与事务边界

### 8.1 第一条有效需求建项

服务端先验证内容是否承载需求；有效时在一个事务中创建项目、项目会话、七阶段实例、第一条客户消息和第一阶段激活事件。事务提交后异步触发自动命名、负责人分配和首次需求引导。

客户端应提供幂等键，避免网络重试生成重复项目。纯问候或无说明附件只产生临时客户端交互，不落项目和会话业务记录。

### 8.2 项目自动命名

命名器读取项目消息摘要，只有 `name_source=AUTO` 且信息达到稳定阈值时才更新。更新应有最短间隔和关键事实差异判断。客户手动改名采用条件更新将来源设为 `MANUAL`；自动更新必须在 SQL 或领域层再次校验来源，防止并发覆盖。

### 8.3 需求确认到合同预付

需求确认命令必须校验成员权限、版本状态和当前阶段。确认成功后写入确认动作和阶段事件，并触发报价生成。

合同阶段仅在签署成功事件和预付款成功事件均存在且有效时完成。两个事件到达顺序不限，每次回调处理后执行同一门槛检查，门槛迁移应幂等。

### 8.4 设计产物发布

所有草图和正式设计版本只有具备主负责设计师或授权审核人的批准记录后，才可发布到客户会话。生成工具创建的版本默认未审核；具备发布权限的设计师人工制作或上传版本时，可以在发布命令中同时执行批准，但必须记录真实批准人和审计。发布服务在同一业务事务中记录批准结果、发布时间和消息卡片，避免“客户看到卡片但版本未批准或未发布”。

### 8.5 尾款与交付

尾款成功后才允许发布合同约定的交付版本。交付确认校验成员权限和具体版本。合同超时任务只处理仍未确认且无争议锁定的交付，并追加自动进入售后的业务事件。

### 8.6 暂停、恢复与关闭／终止

暂停命令必须校验项目权限、可暂停状态和项目当前版本，并使用“当前状态＋版本”的条件更新追加暂停事件。暂停生效后，项目阶段实例进入 `SUSPENDED` 展示态，冻结自动阶段调度、提醒倒计时和项目计划的业务计时，同时保留外部签署、支付等回调事实。暂停期间到达的外部回调只完成验签、幂等入库和审计，不得自动推进阶段。

恢复命令同样采用幂等键和条件更新。服务根据暂停区间、合同规则和未完成任务重新计算里程碑，再追加恢复事件并恢复自动调度。若重排影响合同交付日期或形成重大延期，必须通知客户和主负责设计师并创建升级事项，不能只在后台调整时间。重复暂停、重复恢复或网络重试返回已有业务结果，不产生重复事件。

签约前关闭只能在没有生效合同和成功支付事实时执行，并通过受控终态迁移完成。签约后不得直接把项目改为“已取消”，只能创建 `ProjectTerminationRequest`；合同规则计算、退款或补款、已发生成本、材料交接、争议处理及必要人工审批完成后，才可追加终止结果事件。退款、争议和责任结论不得由 Agent 独立决定。

暂停、恢复、关闭和终止必须与阶段推进、负责人变更、接管、支付回调和交付任务进行并发互斥或版本校验。任何更新行数为零的迁移都按并发冲突处理，禁止无条件重试覆盖其他事务结果。所有命令和状态变化均写入业务审计。

### 8.7 售后复购建项

新项目创建卡包含系统识别且由客户确认的新需求摘要，并说明哪些组织／品牌资料可以选择性复用。客户点击创建时，该摘要作为第一条有效需求，复用 8.1 的原子建项事务和幂等规则；新项目、新会话、七阶段实例、第一条需求消息和激活事件必须一次成功或一次失败。

如果卡片摘要仍不足以构成有效需求，只进入 `/workspace/new` 继续补充，不创建服务器端项目或临时会话。可复用资料通过受权限控制的引用或选择性副本进入新项目；不得复制或混合旧项目合同、付款、产物版本、确认记录和审计历史。

## 9. 权限模型

采用 RBAC 与资源级 ABAC 组合。角色决定基础能力，资源关系和专项授权决定具体项目动作。

客户访问必须满足组织与项目成员关系；不同客户组织之间严格隔离。客户项目成员只能访问授权项目，关键动作还需专项权限。

设计师访问分两级：全局摘要可见和项目完整访问。所有启用的设计师可读取脱敏的项目摘要；主负责、有效协作授权或管理员才可读取完整会话、敏感文件和商业明细。修改、接管和审核需要对应动作权限，不能因“可读摘要”自动获得操作权。

管理员权限也应细分为业务管理、财务、合同、审计和运行诊断，避免一个通用管理员角色无限授权。

前端路由守卫仅用于体验，所有权限由后端资源服务再次校验。下载链接必须短时有效，并在签发前校验项目关系和文件业务归属。

## 10. 自动化安全边界

每个工具定义独立权限和参数约束。Agent 只能使用显式批准的工具，工具层再次校验项目状态、调用主体和业务前置条件。

允许自动执行的典型动作包括普通消息、需求模板、规则内报价、合同草稿、变更单草稿、计划、正常报告、提醒和摘要。

支付确认、签署确认、客户版本确认由真实事件触发。退款、合同终止、争议、投诉、版权与责任认定及记录删除必须进入人工决策流程。任何 Agent 均不得绕过所属模块服务直接写数据库。

客户知识检索必须先做租户、项目与权限过滤，再执行检索。跨客户经验只能使用明确允许的脱敏知识库，不能将原始私有材料作为共享知识来源。

## 11. 外部集成

电子签、支付、邮件、对象存储和生成式设计工具均定义端口与适配器。业务模块依赖内部端口，不依赖供应商 SDK 类型。

外部请求保存业务请求号、供应商请求号和幂等键。回调必须验证签名、来源、金额／主体／订单关联，并保存原始事件摘要和处理结果。重复回调返回成功但不重复迁移状态。

不确定、处理中和失败必须保留为独立状态，不得把超时当作成功或失败终态。可重试任务采用受控重试、退避和死信／人工告警。

## 12. 文件与存储

`common.storage` 管理文件元数据、对象存储键、大小、MIME、哈希和物理读写。`communication`、`artifact`、`commercial` 分别管理文件在消息、项目产物和合同中的业务关系与权限。

上传流程由后端创建授权和记录元数据。前端不得持有 OSS AccessKey，不得仅凭可猜测 URL 获取私有文件。公有作品案例与私有项目文件使用不同 Bucket 或至少不同访问策略；私有对象默认不可公开读取。

需求、合同、报告、草图、正式设计和交付文件按版本归档。物理删除必须受保留期、合同、审计和争议锁定约束。

## 13. API 设计原则

接口统一以 `/api` 开头，统一返回 `Result<T>`。Controller 使用 Jakarta Validation 和 OpenAPI 注解，不返回 Entity。

推荐资源路径如下：

```text
/api/auth/**
/api/portfolio-cases/**
/api/projects
/api/projects/{projectId}
```

## 14. 前端架构

客户工作台以项目为路由上下文，例如 `/workspace/:projectId`；无项目时使用 `/workspace/new`，不在服务端创建空会话。空白页的欢迎语、动态需求模板、未发送输入和附件列表属于客户端草稿状态；离开页面后可直接丢弃，只有满足第一条有效需求规则并提交成功时才进入 8.1 的建项事务。

七阶段进度使用阶段查询 VO 返回当前状态、激活轮次、任务摘要、等待方、预计时间、完成记录和关联版本。当前阶段可返回经权限计算的动作列表；历史阶段只返回只读记录与版本入口，前端不得根据历史状态自行构造修改动作，后端也必须拒绝越权或不符合状态机前置条件的命令。

前端附件草稿支持同一消息多文件、上传状态、失败重试和发送前移除。消息提交携带已完成上传且属于当前用户草稿的文件资产 ID；后端在事务中校验所有权、项目关系、文件状态和数量／大小限制后建立消息附件关系，禁止跨项目复用未经授权的文件 ID。

前端状态按项目隔离，项目切换时取消旧请求或校验响应所属项目，避免消息和文件串入其他项目。关键确认卡的按钮必须展示当前版本和权限状态，提交时携带版本标识与幂等键。

客户桌面端样式延续轻商务设计令牌：浅灰白表面、深色正文、克制暖色强调和语义化业务状态色。三栏信息层级与七阶段进度是结构核心，视觉实现不得退化为技术诊断控制台或通用客服聊天模板。

设计师控制台将全局摘要列表与完整项目详情分开。列表 API 只返回摘要；进入详情时后端重新验证完整访问权限。运行诊断使用独立路由、接口和权限。

实时通信引入后，服务端事件只通知“需要刷新或追加的事实”，不允许客户端凭推送内容自行完成阶段状态。断线重连后以服务端游标补拉消息和事件。

## 15. 审计、可观测性与诊断

业务审计记录真实 actor、显示身份、来源、动作、项目、对象与版本、前后状态、时间、结果、关联请求和接管会话。审计数据追加写入，普通业务用户不得修改。

应用日志使用关联 ID、项目 ID 和事件 ID进行排查，但不得写入密码、完整 Token、密钥、支付敏感数据、私有文件正文或完整模型提示。运行诊断中的 Agent 输入输出也应按权限脱敏并设置保留期。

指标至少覆盖消息处理延迟、阶段停留时间、人工审核 SLA、接管时长、外部回调失败、工具错误、通知失败和升级积压。

平台按全天可提交、可接续服务设计。普通自动化任务可持续运行；涉及人工审核或人工决定的任务由 `notification` 与 `automation` 共同维护 SLA 截止时间、临期提醒和超时升级。客户侧展示业务状态与预计处理时间，不把“全天服务”错误实现为虚构人员在线或所有人工事项即时响应。

## 16. 并发、一致性与任务调度

项目、阶段、产物版本、接管和负责人分配采用乐观锁或条件更新。关键命令以“当前状态＋版本”作为更新条件，更新行数为零时返回并发冲突或重新读取，而不是覆盖。

外部回调和客户端关键命令使用幂等记录。定时任务采用可抢占但不可重复生效的处理方式；单体多实例部署时使用数据库领取、分布式锁或队列表达任务所有权。

需要在事务提交后执行的通知、Agent 调度和工具调用通过 Outbox 或等价可靠事件机制触发，禁止在数据库事务未提交时发送不可撤回外部动作。

## 17. 配置与密钥

通用非敏感默认值放在 `application.yml`。真实数据库口令、JWT 密钥、邮箱密码、OSS AccessKey、支付与电子签密钥只能通过环境变量、密钥管理系统或被 Git 忽略的本地配置提供。

`application-local.yml` 不得提交版本库，也不得作为凭据分发方式。当前本地文件中已经存在的真实敏感值应视为潜在暴露项：实施前进行来源排查、吊销轮换，并避免在技术文档、聊天、日志或测试数据中再次复制。

## 18. 测试策略

采用精简、风险驱动测试，同时把任务耗时和 token 消耗作为测试方案成本，不追求测试数量或覆盖率数字。每个新增测试应对应一个独立且重要的业务、安全或并发风险；相似输入合并为少量代表性场景，不为低风险实现细节批量生成用例。

优先验证：第一条有效需求原子建项、项目隔离、设计师摘要与完整访问边界、需求版本确认、签署与支付双门槛、支付回调幂等、设计审核门槛、接管互斥、关键状态并发迁移、变更回退、交付权限和跨租户文件访问。

开发时先运行受影响模块的定向测试。完整功能完成后原则上只运行一次全量测试和启动验证；只有测试失败、实现继续变化或风险范围扩大时才重复高成本验证。避免相似输入穷举、重复 Mockito 调用验证和低风险实现细节测试。

## 19. 迁移策略

迁移按能力纵向推进，不进行一次性全库重写：

第一步建立新版项目、会话身份、成员权限和审计基础，使第一条有效需求可以直接建项目，不再创建旧咨询需求单。

第二步建立版本化需求基线与七阶段事件模型，将客户工作台切换到项目上下文。

第三步建立商业事件门槛、产物版本、设计审核和交付流程。

第四步接入协调 Agent、专业 Agent、接管和升级，并将旧咨询中可复用的结构化能力迁移至 `automation` 或对应业务模块。

第五步迁移现存数据和调用方，冻结旧咨询创建入口，监控无新写入后下线旧 API、表和定时任务。

每一步都必须提供数据映射、双写或切换策略、回滚方案和定向测试。禁止在未证明无调用和无业务数据依赖前删除旧代码或表。

## 20. 待决技术事项

实施对应模块前仍需确定电子签、支付、邮件和生成式设计供应商；定义价格规则、合同模板、退款规则、修改轮次、交付确认期限和 SLA；确定设计生成工具能否提供合同要求的可编辑源文件。

这些未决项不应阻塞项目、会话、权限、版本、审计和状态机基础模型的设计，但不得以临时假结果完成真实商业状态。
