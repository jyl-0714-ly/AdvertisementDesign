# 广告设计项目协作平台需求分析报告

版本：2.0  
日期：2026-07-28  
状态：需求基线草案，确认后作为产品设计与技术实现依据  
适用范围：客户桌面端、设计师控制端、管理与运行诊断能力、后端业务系统

## 1. 文档目的

本文重新定义平台的产品方向。旧版以“作品顾问、咨询需求单、设计师匹配、三秒匹配和六十秒确认”为核心的业务思路不再作为目标流程。新版采用“项目优先、会话承载、七阶段持续服务”的模式：客户登录后直接进入需求沟通工作台，每个有效需求形成独立项目，系统通过统一的“项目服务团队”身份持续推动项目，设计师在客户无感的前提下监督、审核和接管。

本文描述业务目标、角色、客户体验、七阶段规则、权限、异常流程和验收标准；具体系统架构见《技术设计文档_2.0.md》。

## 2. 产品目标与原则

平台目标是把广告设计项目从首次需求沟通、合同付款、调研、设计评审、交付到售后复购统一在一个可追踪的项目协作空间中完成。

核心原则如下：

- 一个项目对应一个独立会话，并拥有独立的阶段、成员、文件、版本、合同、付款和审计历史。
- 客户侧只有一个对外沟通身份：“项目服务团队”。
- 不向客户展示 Agent、模型、工具调用、自动回复、内部设计师切换或运行诊断。
- 不使用虚构员工姓名、虚构头像、虚构成员列表或虚假在线状态。
- 自动处理与人工处理在客户侧保持连续一致，但后台必须记录真实执行者和操作来源。
- 普通沟通和规则内流程可自动推进；合同、付款、版本确认、交付接收等关键状态只能由真实业务事件触发。
- 已确认内容和已发送消息不可静默覆盖；更正、变更和回退必须留痕。
- 客户隐私按组织、项目、成员权限隔离；跨项目复用只使用经判断相关且允许复用的信息。
- 当前仅设计和实现桌面端，移动端暂不纳入范围。

## 3. 用户与职责

### 3.1 访客

访客可以访问公开首页、服务介绍、公开作品案例、登录和注册页面。访客不能访问项目、会话、文件或任何客户私有数据。

### 3.2 客户组织与项目成员

客户以组织为业务归属，可以拥有多个项目，并邀请同事参与特定项目。

项目成员角色包括：

- 项目管理员／主要联系人：管理项目成员及权限，默认具备需求、合同、付款、设计定稿和交付接收权限。
- 可确认成员：根据明确授权执行指定确认或业务动作。
- 仅评论成员：可查看允许的项目内容并发送消息、评论和标注，不可执行关键确认。
- 仅查看成员：只能查看被授权的项目内容。

每个项目必须指定一名客户侧主要联系人。合同签署、付款、需求确认、报告确认、风格确认、定稿确认和交付接收必须记录真实操作人，并校验其专项权限。

### 3.3 设计师

每个项目有一名主负责设计师。其他设计师可以在获得授权后协作或接管。

所有设计师可以在控制台查看所有项目的必要业务摘要，以便发现风险和进行资源协调；完整会话、敏感文件、合同付款明细、接管、修改和审批能力只授予主负责设计师、明确授权的协作设计师或管理员。摘要不得暴露超出工作所需的客户敏感信息。

主负责设计师负责监督项目、审核设计产物、处理升级事项并在必要时接管沟通。主负责变更由当前负责人或管理员发起，新负责人接受后生效，完整上下文随项目继承，客户侧不显示负责人变化。

### 3.4 管理员

管理员负责全局项目协调、设计师分配、超时与风险处置、规则配置、权限管理、审计查询及运行诊断。管理员不应绕过关键业务动作的真实事件约束。

### 3.5 内部智能协作角色

系统内部包含一个协调 Agent 和七个与阶段一一对应的专业 Agent。内部名称仅用于管理、调度和审计，不得返回客户侧。

协调 Agent 负责共享上下文、阶段调度、规则执行、工具调用、风险识别、人工升级和恢复。专业 Agent 分别服务于需求引导、合同预付款、资料调研、草图风格、审稿定稿、交付尾款和售后复购。

## 4. 项目与会话规则

### 4.1 登录与默认入口

客户登录后直接进入“需求沟通”工作台：

- 有项目时自动打开最近活跃项目。
- 没有项目时显示空白需求沟通页，第一屏包含欢迎语和动态需求模板卡，引导客户先说明设计对象或用途。
- 动态模板根据已输入内容逐项变化，一次突出一个关键问题，但不强制客户按固定问卷填写，客户仍可直接发送完整描述。
- 左侧项目列表支持切换项目、搜索和新建需求。

### 4.2 项目创建

进入空白页面或点击“新建需求”不创建服务器记录。仅当客户发送第一条有效需求时，项目和会话才在同一事务中创建。

有效需求包括：包含设计对象或目的的文字；或者附件并附有用途说明。纯问候、表情或无说明附件不创建项目，系统应引导客户补充用途。欢迎语、动态模板的客户端交互及未发送内容也不得生成服务端临时会话；客户离开空白页后直接丢弃。

项目和会话事务提交后立即异步尝试分配主负责设计师，匹配参考专业适配、工作量和排期；负责人分配不得进入原子建项事务并阻塞建项结果。若暂时无法分配，项目进入内部待分配队列并通知管理员，客户服务流程不中断，也不显示分配失败。

### 4.3 项目名称

项目初始名称为“新项目需求沟通”。系统从聊天中大致识别项目对象和服务类型后自动生成稳定名称，不需要客户确认，也不得在每条消息后频繁变化。

关键事实被纠正时可以再次自动更新。客户可手动修改名称；手动修改后自动命名永久停止，除非客户主动选择“恢复自动命名”。项目名称只显示在左侧项目卡片等项目上下文中，不在聊天顶部重复显示。

### 4.4 项目状态

客户可见项目状态至少包括：进行中、等待客户、处理中、人工审核、已暂停、已取消、售后中。

阶段与项目状态分离：阶段表达业务所处步骤，项目状态表达当前处理态。项目状态变化必须有时间、原因和真实触发来源。

## 5. 客户桌面端工作台

客户工作台采用三栏结构：

- 左栏为项目会话列表，显示项目名称、最后消息摘要、最后消息时间、当前阶段、项目状态、未读或待办提示。
- 中栏为主要聊天区，顶部固定显示完整七阶段进度，正文按时间顺序展示消息和业务卡片，底部为输入区。
- 七阶段进度支持展开当前阶段和历史阶段摘要。当前阶段显示任务、等待方、预计时间和可执行操作；历史阶段只显示完成记录及对应历史版本，不提供越权修改入口。
- 右栏默认显示当前阶段任务、等待方、预计完成时间、已完成记录和当前操作；可切换项目资料与项目信息。

输入区支持文本、图片、常规文件、拖拽上传和截图标注。同一条消息可以携带多个附件；发送前必须显示待发送文件列表，允许客户检查并删除误选文件。暂不支持语音消息和音视频通话。

截图标注必须绑定具体文件与版本，形成结构化修改反馈，包含标注位置、说明和提交人。

整体视觉延续现有轻商务方向：使用浅灰白页面与卡片表面、深色正文、克制的暖色边框或强调色，并使用明确但不过度的业务状态色。界面应体现长期项目协作，不应呈现为技术控制台或普通客服系统。

## 6. 沟通体验

所有团队消息统一显示“项目服务团队”，使用专业、自然、简洁的“我们”口吻。客户发送的消息显示真实客户项目成员名称，以便多人协作时识别发言者，但不得因此暴露其项目外身份或未授权资料。系统应记住已提供的信息、引用具体客户事实、避免重复提问、避免长篇机械模板，并通常一次提出一个明确问题。

客户发送消息后可以立即显示中性处理状态，再以自然短间隔返回内容。已读统一显示“项目服务团队已读”，不显示具体成员在线状态或个人已读头像。

自动消息和人工消息在客户侧保持同一身份。设计师通过内部“接管”和“恢复 Agent”控制回复权，接管期间自动回复暂停。客户要求人工或设计师时，系统以统一身份回应并立即升级给主负责设计师，不显示“转人工”或成员加入提示。

发送前应进行内容与权限校验。已发送消息不可静默编辑；错误内容通过新消息进行明确更正或澄清。

## 7. 七阶段业务流程

### 7.1 需求引导

系统通过动态需求卡和自然对话逐步收集需求，一次突出一个相关问题，同时允许客户自由输入多项信息。

需求达到可确认程度后生成结构化、版本化的需求基线卡。具备权限的客户成员点击“确认需求”后，该不可变版本成为报价、合同、范围判断和变更评估依据。仅由系统判断“信息足够”不能完成阶段。

### 7.2 签订合同预付款

系统在配置的定价规则内生成并发送报价；折扣、特殊条款或规则外价格必须升级人工。

客户通过合同摘要卡查看完整合同并进入电子签署，通过付款卡完成预付款。只有电子签平台返回签署成功且支付渠道返回预付款成功后，阶段才完成并进入资料调研。聊天中的“已签”“已付”或口头同意不得改变真实状态。

### 7.3 资料调研报告

系统结合当前项目、公司知识、隐私隔离后的历史经验、行业与设计专业知识生成版本化调研报告。依据充分且风险正常的报告可自动发送；低置信度、来源薄弱、敏感或异常内容必须人工审核。

客户确认具体报告版本后完成阶段。提出修改则生成新版本，历史版本继续保留。

### 7.4 草图风格敲定

生成式工具可以生成草图和初始方向，但任何向客户交付的设计产物必须先经主负责设计师或获授权审核人审核。

审核通过的草图以版本化评审卡展示。客户选择并确认具体方向和版本后完成阶段。处理期间客户可查看预计完成时间并继续补充信息，但看不到内部生成和审核方式。

### 7.5 审稿定稿

正式设计稿同样必须经过设计师审核后才能发送。客户可预览、标注、提出修改、对比版本并确认具体定稿版本。

定稿后新增要求应对照需求基线、合同范围和修改轮次。超范围或超轮次需求生成变更单和补充报价，不得静默开启无限修改。

### 7.6 交付尾款

尾款状态以支付渠道真实结果为准。尾款成功后发布版本化交付卡，客户可以查看、下载并由授权人员确认接收。

如果客户未在合同期限内确认，系统按照合同约定自动进入售后，并在到期前提示。交付完成需要满足付款及交付／接收规则，不能仅凭聊天推断。

### 7.7 售后复购

售后是长期服务状态，不要求显示为一次性“完成”。原项目会话、交付文件和历史持续可查，客户在原会话中处理售后问题。

识别到新的独立设计需求时，系统发送新项目创建卡，说明可复用和不复用的信息。客户点击创建时，卡片中已经识别并由客户确认的新需求摘要作为第一条有效需求，项目与会话在同一事务中创建；如果摘要尚不足以构成有效需求，卡片只进入空白工作台并继续补充，不创建服务器记录。原项目合同、付款、版本和审计不得与新项目混合。

## 8. 业务卡片与版本

聊天时间线中的关键动作通过业务卡片完成，至少包括：动态需求、需求基线、报价、合同、支付、调研报告、草图评审、定稿评审、变更单、交付、暂停／取消和复购建项。

同一待办可以在右栏显示快捷入口，但聊天卡片是业务时间线的一部分，不得因右栏状态变化而消失。

需求、报价、合同、报告、草图、正式设计和交付物均应版本化。确认动作必须记录项目、对象类型、不可变版本、操作人、权限来源、时间及结果。历史版本不可静默覆盖或物理删除。

文件同时出现在聊天上下文和项目资料区，并自动归类为需求、合同、调研、草图、正式设计或交付。

## 9. 自动推进、人工审核与升级

系统可以在明确规则内自动发送普通消息、需求模板、报价、合同草稿、变更单、项目计划、正常调研报告、提醒和阶段摘要，并调用已批准的电子签、支付、邮件、文件及图像生成工具。

以下事项不得由 Agent 独立完成：退款、投诉裁定、版权争议、责任认定、已签合同终止、业务记录删除、版本化交付物删除，以及其他不可逆或争议性动作。

以下情况自动通知主负责设计师或管理员：低置信度、需求冲突、重复无法推进、明显不满、合同或支付失败、逾期、退款异常、阶段超时和 SLA 超时。

任何草图和正式设计版本发布给客户前，都必须具有主负责设计师或授权审核人的批准记录。生成式工具产生的版本默认处于未审核状态；由有发布权限的设计师人工制作或上传的版本可以在发布动作中同时完成批准，但仍须记录真实批准人和审计。其他产物是否审核由类型、置信度、来源和风险规则决定。审核中对客户只显示业务状态与预计完成时间。

## 10. 计划、SLA 与通知

平台提供全天可发起、可接续的项目服务。自动化能力在规则和权限范围内持续处理普通沟通与任务，不以设计师工作时段中断客户提交；需要人工审核或决定的事项必须显示可理解的处理状态和预计时间，并受可配置 SLA 约束。全天服务不等于承诺所有人工事项即时完成。

正式项目计划在合同签署后依据合同里程碑生成。系统可在规则内动态调整普通任务时间；影响合同交付日期或构成重大延期时，必须通知客户并升级设计师。

不同产物可以配置不同人工审核 SLA。临近 SLA 时提醒负责人，超时后升级管理员。

通知渠道包括站内通知和电子邮件。重要事件包括待确认、电子签、付款、报告完成、设计评审、交付、阶段延期和人工待办。短信和微信通知当前不纳入范围。

## 11. 暂停、取消、变更与回退

客户可以暂停和恢复项目。暂停冻结自动推进和计划计时；恢复后重新计算排期，从当前有效阶段继续。暂停和恢复必须审计。

签署合同前客户可关闭项目。签署后取消必须通过终止申请和合同规则处理，计算退款、已发生成本和材料交接；存在歧义或争议时必须人工决定。

后续需求变化可以受控地重新激活早期阶段，并显示“变更处理中”。之前的阶段完成事件和版本全部保留，后续工作不得静默删除。确认变更后生成新版本并按规则调整费用、范围和计划。

## 12. 客户资料复用与隐私

系统可以维护客户组织资料、品牌资料、偏好和合作历史。新项目只引用与当前需求相关且允许复用的信息，客户可以查看和纠正可复用事实。

历史项目知识用于辅助时必须进行租户隔离、权限过滤和必要脱敏。不得把一个客户的私有聊天、文件、合同、价格或设计资产暴露给另一客户。

## 13. 设计师控制端需求

控制台首页优先展示项目风险、待办、当前阶段、预计与实际耗时及延期，不以合同和支付金额作为首屏重点。

项目详情包括客户可见的完整会话、结构化项目摘要、已确认事项、当前阶段目标、待解决问题、业务记录、文件版本和审计历史。

设计师可以接管和恢复自动处理、审核设计产物、批准或驳回、申请协作、发起负责人变更及处理升级事项。

Agent 置信度、知识引用、失败原因、工具执行和计划动作不进入普通项目详情，而置于管理员或高级排障权限可访问的“运行诊断”页面。

## 14. 非功能要求

### 14.1 安全

密码使用 BCrypt；认证使用 JWT 或同等级机制；所有服务端接口执行角色、租户、项目和动作权限校验。不得在日志、异常或响应中泄露密码、密码哈希、验证码、完整 Token、JWT 密钥、支付密钥、电子签密钥或对象存储 AccessKey。

前端不得直接持有 OSS AccessKey，也不得绕过后端权限直接上传。开发环境真实凭据只能放在不提交版本库的本地配置或环境变量中；已经暴露的凭据必须吊销并轮换。

### 14.2 审计

消息、关键确认、签署、支付、分配、接管、审核、阶段变化、暂停、恢复、取消、变更和工具调用必须记录真实主体、显示身份、来源、前后状态、时间和关联业务对象。

统一对外身份不能替代真实后台主体审计。

### 14.3 一致性与并发

项目创建、关键确认、阶段迁移、支付回调、签署回调、负责人变更和接管状态必须防止重复执行与并发覆盖。外部回调必须幂等，关键状态迁移必须校验当前状态和业务前置条件。

### 14.4 可用性

外部工具短时不可用时应保留业务状态、提供可理解的客户提示并支持安全重试。不可把未知状态误判为支付、签署或交付成功。

## 15. 当前范围外与待配置事项

当前不设计移动端、语音消息、音视频通话、短信或微信通知。

下列事项需在对应功能实施前配置或选型：电子签供应商、支付渠道、邮件服务、生成式设计工具、可编辑源文件能力、价格规则、折扣权限、合同模板、退款规则、修改轮次、交付确认期限和各类 SLA。

## 16. 核心验收场景

- 新客户进入空白页，纯问候不建项，有效需求发送后项目和会话原子创建。
- 项目根据对话自动稳定命名，客户手动改名后不再自动覆盖。
- 客户始终只看到“项目服务团队”，人工接管和恢复过程无界面突变，后台保留真实主体。
- 需求、报告、草图、定稿和交付确认均绑定不可变版本和授权操作人。
- 合同与预付款必须以外部真实成功事件同时满足后才能进入调研。
- 未经设计师审核的草图和正式设计不得发送客户。
- 超范围修改生成变更单，阶段回退保留原完成记录和历史版本。
- 尾款成功后才能按规则交付；客户确认或合同超时后进入长期售后。
- 新需求经客户确认创建独立复购项目，不混合旧项目记录。
- 所有设计师默认只能看到全局必要摘要；主负责设计师、授权协作者和管理员可以在权限范围内访问完整内容并执行获授权操作。
- 暂停、恢复、取消、接管、退款相关处理和关键状态变化均可审计。

## 17. 旧方向处理

旧版需求分析报告保留为历史资料，不再作为开发依据。旧咨询匹配代码、数据库结构和 API 暂不直接删除；后续必须依据技术迁移方案逐项判定为迁移、替换或下线，并在完成数据迁移、调用方替换和回归验证后删除。
